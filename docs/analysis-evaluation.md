# Stage 4 BPM/key evaluation — ground truth and annotation protocol

This describes how BPM and key are **measured**. No detector exists yet, and
that is deliberate: the evaluation is built first so a detector is measured
honestly from its first commit rather than demonstrated on a convenient example.

## Why the ground truth is ours

Three public datasets were investigated and all three rejected:

| Dataset | Audio | Human tempo/key labels | Outcome |
|---|---|---|---|
| GiantSteps tempo/key | **No** — annotations only; audio fetched from Beatport | Yes | Licence **unspecified**; audio commercial |
| FMA | Yes, CC | **No** — `features.csv` is librosa output, `echonest.csv` is a commercial API's | Circular |
| MTG-Jamendo | Yes, CC | **No** — genre/instrument/mood tags only | No labels; annotations CC BY-NC-SA |

Evaluating a librosa detector against librosa-derived labels measures a library
against itself. Evaluating it against Echo Nest or Essentia estimates measures
inter-algorithm agreement, not accuracy — a disagreement cannot be attributed,
because either estimator may be wrong.

So the ground truth is project-owned: a small human-annotated subset of the
existing CC corpus, which the project can keep, redistribute and defend.

## Two fixture sets, with very different standing

### 1. Synthetic — functional validation only

38 deterministic fixtures generated by `musicintel/analysis/fixtures.py`:

- **14 tempo**: click tracks at 60–180 BPM, with every value's double or half
  also present — (60, 120), (70, 140), (80, 160), (90, 180) — so an octave error
  is visible as such. Includes a non-integer tempo (95.5) and a short 10 s case.
- **24 key**: all 12 major and 12 minor, as I–IV–V–I (major) or i–iv–V–i
  (minor, with a major dominant, which is what establishes a minor tonality
  rather than its relative major). Covering all 24 means every relative pair is
  present.

Ground truth is exact by construction, and generation is a pure function of the
fixture id, so repeated runs are byte-identical.

**These cannot substantiate the ≥90% BPM or ≥75% key acceptance targets.** A
click track is the easiest possible tempo case and a cadence the easiest
possible key case. Scoring 100% here says the code runs, not that it works. Any
report using them must say so.

### 2. Real audio — the accuracy harness, currently unlabelled

`eval/fixtures/bpm_key_annotation_manifest.json` — 60 tracks selected
deterministically from the CC corpus (CC-BY 20, CC-BY-SA 28, CC0 12). Rows carry
`track_id`, `path`, `sha256`, title/artist, duration, licence and source, plus:

| Field | Meaning |
|---|---|
| `bpm` | a number, or `"no_stable_tempo"` |
| `key` | a 24-class name, or `"no_tonal_centre"` |
| `annotation_status` | `pending` / `annotated` / `excluded` |
| `annotator`, `annotated_utc`, `notes` | provenance for the label |

**Every row is currently `pending` with null labels.** The manifest is generated
unlabelled and must never be auto-filled. The harness refuses to report accuracy
against unannotated rows.

## Annotation protocol

### BPM

1. Record the **stable global tempo** in BPM where one exists.
2. Where the tempo is not stable or no meaningful pulse exists — free-time,
   ambient, drone, rubato — record `"no_stable_tempo"` and say why in `notes`.
   **Do not** pick a convenient number.
3. Where the music genuinely supports both a half-time and a double-time
   reading, record the tempo you would **tap or count**, and note the
   alternative. Octave tolerance is handled by the metric, not by the annotator
   — so annotate one honest value rather than pre-correcting.
4. Do not round to a "nice" number. If it is 143.2, write 143.2.

### Key

1. Record **one** key in the 24-class representation: a tonic from
   `C C# D D# E F F# G G# A A# B` plus `major` or `minor`.
2. **Enharmonics normalise to sharps.** `Db minor` is stored as `C# minor`.
   Spelling is notation; pitch class is what a detector can recover.
   `musicintel.analysis.keys.parse_key` accepts either and normalises.
3. Where there is no stable tonal centre — atonal, noise, purely percussive —
   record `"no_tonal_centre"` with a reason. **Do not force a key.**
4. Where you are torn between a key and its **relative** major/minor, record the
   one whose tonic the music resolves to and note the uncertainty. These are the
   confusions the metric exists to diagnose, so an honest note is worth more
   than a confident guess.
5. Modal material: record the closest major/minor and note the mode.

### Exclusions are data

`no_stable_tempo` and `no_tonal_centre` are **named exclusion categories**, not
missing values. They are removed from the accuracy denominator and reported with
counts. Silently dropping them would flatter the score; counting them as wrong
would penalise a detector for correctly declining to answer.

## Metrics

### BPM

- **Raw accuracy**: `|pred − truth| / truth ≤ 0.02`.
- **Octave-tolerant accuracy**: reported **separately**, accepting ×½, ×1, ×2.
  Triple-time (×⅓, ×3) is reported separately again.
- **Raw-error distribution**: p50/p75/p90/p95/p99, min, max, mean.
- **Explicit 2× and ½× counts** — the diagnostic distinguishing "wrong" from
  "off by an octave".

Raw and octave-tolerant are never merged into one number.

### Key

- **Exact 24-class accuracy.**
- **MIREX weighted score**: exact 1.0, perfect fifth 0.5, relative 0.3,
  parallel 0.2, other 0.0.
- **24×24 confusion matrix.**
- **Relation breakdown**: exact / relative / parallel / dominant / subdominant /
  other. Dominant and subdominant both score 0.5 but are reported apart, because
  they are different musical mistakes.

A bare key accuracy is never reported alone.

### Denominators

- **evaluable** — truth exists and the detector answered.
- **excluded** — truth says the quantity is undefined. Removed from the
  denominator, reported by name.
- **failed** — the detector raised or returned nothing. Counted **as wrong**. A
  crash is not an exemption, or a detector could improve its score by failing on
  hard material.

## Performance

Timing is **feature extraction + BPM + key, excluding audio decode**, measured
**warm**, reported as p95 over at least 100 measurements where the fixture set
allows.

Decode is excluded deliberately: it is already inside the Stage 3 latency budget
(~120 ms of a ~200 ms median), and counting it twice would misrepresent both.
Components — decode, features, BPM, key, total — are reported separately so the
split is visible.

**The <200 ms target is not assumed to be achievable.** It will be measured.

## Sample-rate note, recorded not acted on

Recognition decodes at **11,025 Hz** (Nyquist 5,512 Hz). Synthetic fixtures are
generated at **22,050 Hz**, the rate key-detection work conventionally assumes.
Whether key detection needs the higher rate on real audio is **not established**;
if it does, the cost is a second decode, and that trade-off will be measured
when a detector exists. **The recognition decode rate is not changed
speculatively.**

## Architecture boundary

`musicintel/analysis/` does not import `musicintel/recognition/`, and
recognition does not import analysis — a test asserts the second direction.
`/v1/identify` is untouched; `/v1/analyze` remains a separate future endpoint.
Analysis is not added synchronously to the identify path, whose accepted p95 is
296.3 ms against a 300 ms bar.
